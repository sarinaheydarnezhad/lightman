# Lightman

Offline flashcard mobile foundation. Business data flows through use cases and repository interfaces; development adapters reset on restart. Zustand holds only transient UI state.

## Start and verify

Install Node.js 22.13+ and pnpm 10.15.1 (for example, using Corepack), then run `pnpm install --frozen-lockfile`, `pnpm start`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm format:check`, `pnpm expo:check`, and `pnpm config:check`. Run `pnpm android` for a local Android build, or `pnpm exec expo prebuild --platform android --no-install` to inspect generated native configuration. Android native builds require the Android SDK. iOS prebuild requires macOS or Linux, and local iOS native builds require macOS/Xcode.

## Architecture

`src/app` contains only Expo Router routes and composition. `features/*/presentation` renders screens and loads them through `core/application` use cases; `domain` owns entities, validation, and repository contracts; `data` supplies replaceable adapters. `core/ports` holds shared contracts, `core/composition` binds them, `shared` holds UI primitives and theme, and `store` holds small session UI state. Presentation never imports data adapters. Domain and application use cases never import React Native, Expo, Zustand, or adapter implementations. The composition root can bind a future SQLite adapter without changing use cases, presentation, or domain.

## Performance rules

- Keep deck/card/review collections behind repositories, never in Zustand. The small development seed is explicit in `core/composition/development-seed.ts`.
- Pass identifiers or narrow selectors instead of large objects down component trees.
- Memoize when profiling or a clear render boundary justifies it.
- Avoid expensive render work, gesture callbacks, and animation worklets.
- Deck and card collections use `FlatList` with stable domain IDs; apply the same approach to other growing collections.
- Keep domain logic independent of UI rendering.

## Haptic feedback

Study haptics are presentation feedback only: `core/ports/haptic-feedback.ts` defines semantic events, composition reads `UserSettings.hapticsEnabled` from the in-memory repository, and the Expo adapter selects native effects. A failed/suppressed native effect never blocks an action. Revealing gives one subtle cue, and both buttons and swipes give the same result cue only after the presentation is accepted. A swipe can also give one light distance-threshold cue per gesture; crossing back and forth never repeats it, and a cancelled swipe has no answer-result cue. Velocity-only flicks give the result cue on acceptance. The preference defaults on and is controlled in Settings; reduced motion does not change it. Haptics never replace the visible answer, status, or accessible controls. No haptics run on animation frames or on every navigation event.

## Pronunciation

`SpeechService` hides `expo-speech` and device voice IDs. Study cards and card details pronounce only the front term after a user presses the accessible audio button; a second press stops it. New cards, screen changes, and unmounts stop previous speech. No speech work blocks app startup or study actions. The service queries voices lazily, caches a nonempty inventory, serializes stop/start, and ignores stale completion callbacks.

Deck language is the content language and wins over all speech settings. `UserSettings.preferredSpeechLanguage` is a fallback when no deck language is supplied; the English US/UK accent preference applies only to English voices. A deck's explicit regional language wins over a conflicting accent. If neither language is set, a small script check recognizes Persian or Arabic, otherwise the device default voice is preferred. Voice selection uses locale match, quality, default status, and stable name/ID ordering. A missing preferred accent falls back to another voice for the same language. Unsupported languages or missing voices return an unavailable state instead of choosing an unrelated language.

Speech is entirely device-provided; the app makes no audio network requests and stores no audio files. The web adapter offers only voices the browser marks as local, and is unavailable without one. Android voice engines and installed language data vary by device; Expo's Android voice metadata does not identify voices that depend on network services, so offline audibility must be checked on target devices with a local voice installed. Physical iOS devices may be silent when the ringer is muted. The UI never claims that a playback request was audible. Preferences stay in the existing in-memory settings repository until persistent storage is introduced.

Store identifiers in `app.json` are provisional and must be owned by the publisher before release. EAS credentials and project linkage are configured when builds begin.

SDK 57's `expo-build-properties` plugin enables iOS scene support for builds made with Xcode 27. Regenerate native projects after changing app config. Store artwork, signing credentials, and on-device QA are release work outside this foundation.

## Design system

`src/shared/theme/values.json` is the single source of visual values. `tokens.ts` exposes typed colors, typography, spacing, radii, heights, and elevation. The NativeWind configuration reads the same values: semantic colors map to CSS variables that `ThemeProvider` sets on its root view for light, dark, or OLED. Use semantic utilities such as `bg-surface`, `text-primaryText`, `p-xl`, `rounded-md`, and `text-headingLarge`; avoid one-off values. Native properties that need color props (Lucide icons, indicators, text selection, navigation) read `useThemeColors()`. Cards use the shared shadow tokens via native style for iOS shadow and Android elevation.

The active appearance preference lives in `useUiStore` for this session and is mirrored to the in-memory `UserSettings` repository through a use case. `system` resolves system light to light and system dark to dark; OLED is explicit and uses `#000000` as its base. Storage can be added at the repository boundary later. Settings exposes all four preferences. In development, Settings links to `/design-system`, which previews every primitive and appearance; the route is intentionally available by direct URL for internal inspection.

Core primitives live in `src/shared/ui`: `Screen`, `Text`, `Button`, `IconButton`, `Card`, `Input`, `Divider`, `Badge`, `Chip`, `Tab`, `EmptyState`, and `LoadingState`. `Screen` uses safe area insets on all edges and a fluid centered content limit for phones and tablets. `Text` and `Input` support alignment, including RTL-aware start/end text alignment in `Text`; flex row components preserve native RTL mirroring. The UI uses font scaling, roles and state for actions/tabs, labels for icon controls, and readable theme-specific semantic contrast. Full localization, persisted preference, and full accessibility/device audits remain future work.

## Application shell

`src/app/_layout.tsx` keeps the existing provider order: gesture root, safe area, theme, bootstrap gate, then the native stack. `src/core/bootstrap/initialize-application.ts` is the one asynchronous startup entry point; it explicitly seeds the development repositories and initializes default settings. The gate tracks boot, initializing, ready and error states, provides loading and retry screens, and never runs setup in render. Feature screens stay in their `features/*/presentation` folders; route files only compose screens and read typed route parameters. The existing five tabs use JavaScript tabs with native safe-area handling and the root stack presents secondary screens. The tab navigator owns the bottom inset; stack headers own the top inset. `src/shared/navigation/safe-area.ts` supplies the corresponding `Screen` edges so they are not counted twice.

Secondary routes are `/decks/create`, `/decks/[deckId]`, `/decks/[deckId]/edit`, `/decks/[deckId]/cards`, `/decks/[deckId]/cards/create`, `/decks/[deckId]/cards/[cardId]`, `/decks/[deckId]/cards/[cardId]/edit`, `/study/[sessionId]`, `/vocabulary/helper`, and `/settings/appearance`. Expo Router's existing typed-routes setting generates navigation types when the dev server starts; links use route literals or pathname/params objects, and dynamic screens type `useLocalSearchParams` by pathname. Home, deck list/details, card details, and create/edit/archive flows use application use cases; their focus-aware loaders refresh when navigation returns. Analytics and study remain placeholders until those features have behavior.

Deck management lives in `features/decks/presentation`: `DecksScreen` loads the active deck list and actual card counts through its view model; `DeckListItem` renders data without storage calls; `DeckForm` owns temporary field state and validation; `DeckEditorScreen` submits to use cases and routes create to the list or edit to details; `DeckDetailsScreen` displays saved content settings and confirms archive before the use case hides it from active lists. Search is trimmed and case-insensitive in `DeckRepository.list`; the view model supports current-data sorts by updated date or name without presenting unsupported analytics. The form offers English, Persian, Arabic, and a custom BCP 47 tag; an unedited regional tag is preserved. Per-deck alignment and semantic size control the reading preview and card text; they do not switch app-wide direction. Duplicate deck names are allowed, while IDs remain stable. Archiving retains the repository entity by ID. There is no network dependency or durable storage: development data resets on restart, and production begins empty. Study remains a placeholder route and no study statistics are inferred from deck updates.

Card management uses `CardListScreen` with a deck-scoped virtualized list, category choices and local search through `useCardListViewModel`; `CardListItem` has no storage access. `CardForm` shares create/edit field state and offers structured examples with sentence, translation and notes; `CardContent` shares front/back presentation between form preview and details. A card inherits alignment and semantic typography from its parent deck. Create routes to card details; edit dismisses to existing details; confirmed archive dismisses to the deck's card list. Read and write hooks call the use cases, which validate the deck relationship and delegate to `CardRepository`. Repository search covers term, phonetic, category and meaning, normalizes whitespace and excludes archived cards; category filtering is exact and case-insensitive. Active counts use a repository count operation instead of loading every card into a screen. `CardSort` prepares alphabetical, created and updated ordering without exposing unsupported review filters. Form values stay local and buttons guard rapid saves and archives. No study scheduling or review calculations are performed.

## Domain and persistence contracts

`Deck`, `Card`, `CardReviewState`, `ReviewEvent`, `StudySession`, and `UserSettings` live under feature `domain` folders. IDs are opaque strings. `Instant` is a validated UTC timestamp with milliseconds, `CalendarDate` is an ISO day without a time zone, and `LocalTime` is a 24-hour `HH:mm` wall-clock time. Language tags accept basic BCP 47 syntax such as `en` and `fa-IR`. The single `AppClock` source supplies current instants in use cases; reminder local times and due calendar days stay distinct from timestamps. The future scheduler must decide how local days are interpreted in each time zone. No SRS intervals or streaks are computed yet.

`DeckRepository` offers create/get/list/search/update/archive. `CardRepository` adds deck-scoped lists, search, category filtering and active counting. `ReviewRepository` stores state and immutable event history, with a business-level `record` operation that applies an event and its state together. `SettingsRepository` gets/updates settings. All return domain entities or `null` for absent lookups; commands raise `AppError` codes such as `validation`, `not-found`, `conflict`, or `persistence`. Use cases translate unexpected adapter failures to a safe persistence message. Archives are soft: the normal lists hide archived entities, while historical review events remain append-only.

`core/ports/repositories.ts` bundles only interfaces. `core/composition/repositories.ts` is the single adapter binding, and `core/composition/application.ts` injects those contracts plus the existing clock and ID generator into `createApplication`. In-memory implementations use private Maps and return copies; the UI never reads those Maps. A future SQLite adapter implements the same interfaces and is selected in composition. `core/composition/development-seed.ts` adds four small decks (including an empty deck), four cards (including multiple examples, optional fields and RTL content), two review states and two events only during development startup, idempotently; production starts with no decks. Default settings are initialized separately for either environment. No internet, database, authentication, or sync is used.

The presentation import rule is checked by `test/architecture.test.ts`: domain and use cases cannot import platform frameworks or adapters, and presentation cannot import data adapters. Zustand holds only `themePreference` and `selectedDeckId`; repositories own every business collection. Run the quality checks above for contract, validation, adapter, use-case, seed, and screen-flow coverage.
